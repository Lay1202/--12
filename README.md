# 과제 12: 퀵 정렬의 피벗 선택에 따른 성능 비교

첫 번째 원소(First), 무작위 원소(Random), 세 원소의 중앙값(Median-of-Three)을 피벗으로 쓰는 퀵 정렬을 구현하고 숫자 비교 횟수를 측정했습니다. 전체 실행 로그는 `quick_result.txt`에 있습니다.

- 빌드: `gcc -O2 -o quick_pivot quick_pivot.c` (Visual Studio에서는 Release / x64 권장)
- 데이터: 0 ~ 1,000,000 사이 무작위 정수(중복 허용). 각 크기마다 하나의 원본을 만들고 세 방법에 같은 복사본을 줍니다.
- 분할 알고리즘: 세 방법 모두 같은 Lomuto 분할을 씁니다. 선택한 피벗을 구간 맨 앞으로 옮긴 뒤 나머지 원소를 피벗과 비교하며 분할하고, 피벗을 마지막에 제자리로 보냅니다. 피벗을 고르는 함수만 다릅니다.
- 비교 횟수: 분할에서 원소와 피벗을 비교한 횟수와 Median-of-Three에서 중앙값을 정하느라 한 값 비교(분할마다 2~3회)를 모두 셉니다. 루프 조건, 무작위 위치 생성, 데이터 교환은 세지 않습니다.
- 난수: 자체 xorshift 생성기를 쓰고 시드를 고정했기 때문에 실행할 때마다 결과가 같습니다.
- 검증: 모든 정렬 후 오름차순 여부와 원본과의 합·제곱합 일치(원소 유실 방지)를 확인했고 전부 통과했습니다.

## 2. 분석

### 크기 증가에 따른 변화
무작위 데이터에서 세 방법 모두 n이 2배가 될 때 비교 횟수가 2배보다 약간 더 늘어납니다(평균 기준 n=1,000에서 약 1.1만 회, n=20,000에서 약 33만 회). 이는 퀵 정렬의 평균 비교 횟수가 n log n 규모로 증가하기 때문입니다. First와 Random의 평균은 이론식 2(n+1)H_n − 4n(H_n은 조화수)과 잘 맞습니다. 
예를 들어 n=20,000에서 이론값은 약 339,000이고 측정 평균은 338,593(First), 340,238(Random)입니다. 반면 정렬된 입력에서 First는 n(n−1)/2 그대로(n=20,000에서 199,990,000회) n²으로 증가해 n이 2배가 되면 4배가 됩니다.

### 방법별 성능 차이와 원인
- **First:** 무작위 데이터에서는 첫 원소가 구간의 임의의 값이라 분할이 평균적으로 적당히 나뉘어 평균 성능을 냅니다. 하지만 입력이 정렬되어 있으면 첫 원소가 항상 최솟값이라 분할이 0개 / n−1개로만 나뉘어 비교가 n(n−1)/2가 됩니다. 즉 입력 상태에 따라 최악이 됩니다.
- **Random:** 입력과 상관없이 피벗이 균등하게 뽑히므로 어떤 입력에서도 평균 성능을 기대할 수 있습니다. 정렬된 입력에서도 355,579회(n=20,000)로 First의 약 1/560입니다. 하지만 무작위 데이터에서는 First와 평균이 거의 같고(340,238 vs 338,593), 단일 실험에서는 운에 따라 가장 나쁠 수도 있습니다(n=20,000에서 369,428).
- **Median-of-Three:** 세 값의 중앙값은 극단값이 될 확률이 낮아서 분할이 더 균형 있게 나뉩니다. 그 결과 평균 비교 횟수가 First/Random보다 5~6% 적었고(n ≥ 4,000), 크기가 클수록 격차가 약간 커졌습니다. 정렬된 입력에서는 가운데 원소가 정확한 중앙값이라 분할이 완벽하게 반으로 나뉘어 약 27만 회(n=20,000)로 가장 적었습니다.
- **Median-3의 비용:** 중앙값을 정하느라 분할마다 비교가 2~3회 추가되는데, 작은 구간이 많은 n=1,000에서는 이 추가 비용이 분할 개선 이득과 거의 상쇄되어 이득이 1%에 그쳤습니다(단일 실험에서는 오히려 더 많았음). n이 클수록 이득이 비용을 앞섭니다.

### 결론
실험 결과 가장 효과적인 방법은 **Median-of-Three**였습니다. 무작위 데이터 평균에서 모든 크기에서 가장 적었고, 정렬된 입력에서도 가장 적었습니다. Random은 입력 상태와 무관하게 최악을 피할 수 있다는 점이 장점이지만 무작위 데이터에서는 이득이 없고, First는 구현이 가장 단순하지만 정렬된 데이터에 매우 취약합니다.

## 3. [보너스] 재귀적 vs 반복적 퀵 정렬

반복적 구현은 `malloc`으로 만든 배열을 스택으로 써서 (lo, hi) 구간을 push/pop합니다. 재귀 호출과 같은 순서(왼쪽 → 오른쪽)로 구간을 처리하므로 같은 분할을 하고, 비교 횟수도 151,657회로 정확히 같았습니다. 데이터 크기 10,000, Median-of-Three에서 원본 복사 시간을 제외하고 정렬 시간만 재서, 같은 데이터로 500회씩 3라운드(총 1,500회)의 평균을 구했습니다.

| 빌드 | Recursive | Iterative |
|---|---:|---:|
| gcc -O2 | 0.6013 ms | 0.5923 ms |
| gcc -O0 | 1.3229 ms | 1.3467 ms |

**분석:** 두 방식의 차이는 1~2% 수준으로 사실상 같으며, 최적화 여부에 따라 우열이 바뀔 정도입니다. 실행 시간의 대부분은 분할 루프(약 15만 번의 비교와 교환)가 차지하고 두 방식이 이 부분을 똑같이 수행하기 때문입니다. 차이가 나는 부분은 구간을 넘기는 방식뿐입니다. 재귀는 함수 호출과 복귀(호출 스택 프레임 생성)마다 비용이 들고, 반복은 직접 만든 스택에 push/pop하는 비용과 `malloc/free` 비용이 듭니다. 이 두 비용은 서로 비슷하고 분할 작업에 비해 매우 작습니다. 따라서 반복 방식의 실질적 장점은 속도가 아니라 호출 스택 깊이 제한을 피하는 안정성(최악의 경우에도 힙에 스택을 둘 수 있음)입니다. 측정 값은 컴퓨터와 컴파일러 설정에 따라 달라지므로, 제출 환경(Visual Studio Release)에서 다시 실행한 값으로 README의 이 표를 갱신하는 것을 권장합니다.
